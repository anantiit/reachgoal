ArrayList - What/Why/When

Slide 4

Dynamic Array Implementation

📌 What is ArrayList?

  • Resizable array implementation of List interface
  • Default capacity: 16, grows by 1.5x (16 → 24 → 36...)
  • Contiguous memory storage
  • Random access: O(1), Append: O(1) amortized
  • Insert/Remove middle: O(n) - shifts elements

💡 Why Use / ✅ When:

  • Lightning-fast random access by index
  • Memory efficient (Only 4 bytes overhead)
  • Best cache locality
  • Reading > modifying
  • Appending to end
  • Default choice - 99% of use cases

❌ Don't Use When:

  • Frequent insertions at beginning (O(n) shifts)
  • Middle insertions common
  • Need thread-safety (use CopyOnWriteArrayList)
// ✅ GOOD: Fast random access and append
List<String> names = new ArrayList<>();
names.add("Alice");        // O(1)
names.add("Bob");
String first = names.get(0); // O(1) - instant

// ✅ GOOD: Pre-size if known capacity
List<User> users = new ArrayList<>(1000); 

// ❌ ANTI-PATTERN: Insertions at beginning
for (int i = 0; i < 1000; i++) {
    // O(n) each time - SLOW! Shifts array right
    names.add(0, "Item"); 
}

LinkedList - What/Why/When

Slide 5

Doubly-Linked Node Structure

📌 What is LinkedList?

  • Doubly-linked list: Each node has prev/data/next
  • Implements List AND Deque
  • No capacity - grows one node at a time
  • Random access: O(n), Ends operations: O(1)
  • Memory: 40 bytes per element (10x ArrayList!)

💡 Why Use / ✅ When:

  • O(1) operations at both ends
  • Queue/Deque implementation (addFirst, removeLast)
  • No resizing - Grows node-by-node
  • Efficient iterator-based insertions

❌ Don't Use When:

  • Random access needed (use ArrayList)
  • Memory constrained (use ArrayList)
  • General-purpose List (use ArrayList)
  • Slower iteration (pointer chasing)
// ✅ GOOD: Using as Deque (queue ops)
Deque<String> queue = new LinkedList<>();
queue.addFirst("First");  // O(1)
queue.addLast("Last");    // O(1)
String head = queue.removeFirst(); // O(1)

// ❌ ANTI-PATTERN: Random access
LinkedList<String> list = new LinkedList<>();
list.add("A"); list.add("B"); // ... 1000 items
// O(n) - traverses 500 nodes to find it!
String middle = list.get(500); 

// Reality Check: ArrayList beats LinkedList 
// 99% of the time. Only use LinkedList for 
// specific deque operations!

HashSet - What/Why/When

Slide 7

Hash Table-Based Unique Collection

📌 What is HashSet?

  • Backed by HashMap (elements = keys, dummy value)
  • Default capacity: 16, load factor: 0.75
  • Hash-based: No guaranteed order
  • O(1) add, remove, contains
  • Java 8+: Bins convert to trees when > 8 elements

💡 Why Use HashSet?

  • ✅ Automatic uniqueness - No manual duplicate checking
  • ✅ O(1) lookups - Instant membership testing
  • ✅ Fast add/remove - Constant time operations
  • ✅ Set operations - Union, intersection, difference

❌ Don't Use When:

  • Need ordering (use LinkedHashSet or TreeSet)
  • Allow duplicates (use List)
  • Need index access (use List)
// ✅ GOOD: Remove duplicates
List<String> withDupes = Arrays.asList("A", "B", "A", "C");
Set<String> unique = new HashSet<>(withDupes);
// unique = [A, B, C] - duplicates removed

// ✅ GOOD: Fast membership check - O(1)
Set<String> validCodes = new HashSet<>(
    Arrays.asList("US", "UK", "CA")
);
if (validCodes.contains("US")) { // Instant!
    processOrder();
}

// ✅ GOOD: Set operations
Set<Integer> set1 = new HashSet<>(Arrays.asList(1, 2, 3));
Set<Integer> set2 = new HashSet<>(Arrays.asList(3, 4, 5));

set1.retainAll(set2); // Intersection: {3}
// set1.addAll(set2); // Union
// set1.removeAll(set2); // Difference

Set Implementations - Comparison

Slide 8

LinkedHashSet & TreeSet & EnumSet

LinkedHashSet - What/Why/When

What: HashSet + insertion order preservation
Why: Predictable iteration, ordered unique collection
When: ✅ Need unique + insertion order | ✅ Deterministic testing | ❌ Order doesn't matter (use HashSet - faster)

TreeSet - What/Why/When

What: Red-Black tree, sorted order, NavigableSet
Why: Automatic sorting, range queries (ceiling, floor, subSet)
When: ✅ Need sorted unique collection | ✅ Range ops required | ❌ Order not needed (use HashSet - 3-5x faster)

EnumSet - What/Why/When

What: Bit vector for enums (1 bit per constant)
Why: 64x more memory efficient, O(1) operations, lightning fast
When: ✅ Always use for enum sets (never HashSet for enums!) | ✅ Flags, permissions, options

Performance (100k operations):

EnumSet:         5 ms    (bit operations)
HashSet:        45 ms    (hash operations)
LinkedHashSet:  52 ms    (hash + linked list)
TreeSet:       180 ms    (tree operations)

hashCode() & equals() Contract

Slide 9

Critical for Hash-Based Collections

The Contract:

  1. If a.equals(b) is true → a.hashCode() == b.hashCode() MUST be true
  2. If a.hashCode() != b.hashCode() → a.equals(b) MUST be false
  3. Consistency: Multiple invocations return same value if object unchanged

Common Mistakes:

  • Override equals() but not hashCode() → broken HashMap/HashSet
  • Mutable keys → lost entries
  • Poor hash function → all collisions, O(n) performance
// ✅ BEST PRACTICE: Override both
public class CustomKey {
    private final String field1;
    private final int field2;
    
    // Standard equals implementation
    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (!(obj instanceof CustomKey o)) return false;
        return field2 == o.field2 && 
               Objects.equals(field1, o.field1);
    }
    
    @Override
    public int hashCode() {
        // Generates good hash distribution
        return Objects.hash(field1, field2);
    }
}

HashMap - What/Why/When

Slide 10

The Workhorse of Java Collections

📌 What is HashMap?

  • Array of Node<K,V>[] buckets (default: 16, power of 2)
  • Load factor: 0.75 (resize when 75% full)
  • O(1) get/put/remove (average case)
  • Java 8+: Bins → trees when > 8 collisions
  • Allows: One null key, multiple null values

💡 Why Use / ✅ When:

  • O(1) key-value lookups - Instant retrieval by key
  • Need fast key lookups (caching, indexing, counting)
  • Rich API (Java 8+) - compute, merge, computeIfAbsent
  • General purpose - Default Map choice
// ✅ GOOD: Frequency counting
Map<String, Integer> freq = new HashMap<>();
for (String word : words) {
    // Increment counter atomically
    freq.merge(word, 1, Integer::sum); 
}

// ✅ GOOD: Caching expensive results
Map<String, Result> cache = new HashMap<>();
Result result = cache.computeIfAbsent(key, 
    k -> expensiveComputation(k));

// ✅ GOOD: Indexing by ID
Map<Long, User> index = new HashMap<>();
for (User user : users) {
    index.put(user.getId(), user);
}
User found = index.get(12345L); // O(1) lookup

LinkedHashMap - Predictable Iteration

Slide 11

HashMap with Ordering

Two Ordering Modes:

  1. Insertion order (default): Elements returned in insertion sequence
  2. Access order: Most recently accessed moves to end (LRU)

Use Cases:

  • Cache with predictable iteration
  • Maintaining insertion order (e.g. JSON serialization)
// ✅ BEST PRACTICE: LRU Cache Implementation
class LRUCache<K,V> extends LinkedHashMap<K,V> {
    private final int capacity;

    LRUCache(int capacity) {
        // initialCap, loadFactor, accessOrder=true
        super(capacity, 0.75f, true); 
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(
            Map.Entry<K,V> eldest) {
        // Evicts oldest entry automatically
        return size() > capacity;
    }
}

TreeMap - Sorted & Navigable

Slide 12

Red-Black Tree Implementation

Characteristics:

  • O(log n) for get, put, remove
  • Sorted by keys (Comparable or Comparator)
  • No null keys (values allowed)
  • Use Cases: Sorted maps, range queries, timelines

NavigableMap Operations:

  • ceilingKey(key): Least key >= given key
  • floorKey(key): Greatest key <= given key
  • higherKey(key): Least key > given key
  • subMap(from, to): View between keys
  • headMap(to): View of keys < to
// Time-based mapping example
TreeMap<LocalDateTime, Event> schedule = 
    new TreeMap<>();
    
schedule.put(time1, event1);
schedule.put(time2, event2);

// Find the next upcoming event
LocalDateTime now = LocalDateTime.now();
Map.Entry<LocalDateTime, Event> next = 
    schedule.ceilingEntry(now);

// Get all events for today
SortedMap<LocalDateTime, Event> todayEvents = 
    schedule.subMap(startOfDay, endOfDay);

ConcurrentHashMap - What/Why/When

Slide 13

Thread-Safe High-Performance Map

📌 What is ConcurrentHashMap?

  • Thread-safe map without global locking
  • Lock-free reads, CAS + bin-level locking for writes
  • No null keys or values
  • Weakly consistent iterators (no ConcurrentModificationException)
  • Atomic operations: compute, merge, putIfAbsent

💡 Why Use / ✅ When:

  • Thread-safe without synchronization
  • High concurrency (Scales with threads)
  • Atomic updates (counters, accumulators)
  • 10-100x faster than synchronized HashMap

❌ Don't Use When:

  • Single-threaded (use HashMap)
  • Need null keys/values
  • Strict consistency required
// ✅ GOOD: Thread-safe counter
ConcurrentHashMap<String, Long> counters = 
    new ConcurrentHashMap<>();

// Atomic increment from multiple threads
counters.merge("requests", 1L, Long::sum); 

// ✅ GOOD: Thread-safe caching
ConcurrentHashMap<String, User> cache = 
    new ConcurrentHashMap<>();
User user = cache.computeIfAbsent(id, 
    this::loadUserFromDB);
// Only one thread loads for same id!

// ✅ GOOD: Multi-threaded counting
words.parallelStream().forEach(word -> 
    wordCount.merge(word, 1L, Long::sum));

Java 8+ Map Compute Methods

Slide 14

Atomic Operations for Concurrent Updates

Advantage: Atomic, thread-safe, cleaner than the legacy get-check-put pattern.

compute(key, BiFunction)

Always computes new value (key present or absent). Atomic.

map.compute("counter", 
    (k, v) -> v == null ? 1 : v + 1);

computeIfAbsent(key, Function)

Compute only if key absent. Common pattern: initialize on access.

map.computeIfAbsent("key", 
    k -> expensiveComputation());

computeIfPresent(key, BiFunction)

Compute only if key present.

map.computeIfPresent("key", 
    (k, v) -> v * 2);

merge(key, value, BiFunction)

Merge new value with existing.

map.merge("key", 1, Integer::sum); 
// Increment counter

Queue & Deque - What/Why/When

Slide 15

FIFO and Double-Ended Queues

ArrayDeque - Best Stack/Queue

What: Resizable circular array, O(1) both ends.
Why: Faster than Stack & LinkedList, no null restriction.
When: ✅ Stack (LIFO), Queue (FIFO), Deque operations

PriorityQueue - Priority Processing

What: Binary heap, O(log n) insert/remove.
Why: Automatic priority ordering, smallest element first.
When: ✅ Task scheduling, top-K problems

BlockingQueue - Thread-Safe

When: ✅ Multi-threaded work queues, producer-consumer

// ✅ GOOD: ArrayDeque as Stack
Deque<String> stack = new ArrayDeque<>();
stack.push("First");
String top = stack.pop(); 

// ✅ GOOD: Priority task queue
PriorityQueue<Task> tasks = new PriorityQueue<>(
    Comparator.comparingInt(Task::getPriority)
);
tasks.offer(new Task("Low", 3));
tasks.offer(new Task("High", 1));
Task urgent = tasks.poll(); // Gets "High"

// ✅ GOOD: Producer-Consumer
BlockingQueue<Work> queue = 
    new ArrayBlockingQueue<>(100);
// queue.put(work); // Blocks if full
// Work w = queue.take(); // Blocks if empty

Immutable Collections - What/Why/When

Slide 16

True Immutability (Java 9+)

📌 What are Immutable Collections?

  • Truly immutable (not just unmodifiable views)
  • Factory methods: List.of(), Set.of(), Map.of()
  • No null allowed (NullPointerException)
  • Thread-safe without synchronization

💡 Why Use / ✅ When:

  • Thread-safe - Share across threads safely
  • No defensive copies - Return directly from methods
  • Constant data (configurations, lookup tables)
  • Map keys/Set elements (ensure hashCode consistency)
  • vs Collections.unmodifiable: List.copyOf() is independent, unmodifiableList() is a view
// ✅ GOOD: Constants
private static final List<String> STATUS =
    List.of("PENDING", "APPROVED");

private static final Map<String, String> ERR = 
    Map.of("E01", "Invalid", "E02", "Missing");

// ✅ GOOD: Return safely (no defensive copy!)
public List<String> getPermissions() {
    // Safe!
    return List.of("READ", "WRITE"); 
}

// ✅ GOOD: Build then freeze
List<String> temp = new ArrayList<>();
// ... build list ...
// Now immutable independent copy
List<String> immutable = List.copyOf(temp);

Comparable vs Comparator

Slide 17

Sorting Strategies

Comparable<T> (Natural Ordering):

  • Implemented by class itself
  • Single ordering
  • compareTo(T other)
  • Examples: String, Integer, LocalDate

Comparator<T> (External Ordering):

  • External to class, Multiple orderings possible
  • Functional interface
  • Factory methods: comparing(), comparingInt/Long()
  • Utilities: reversed(), nullsFirst(), nullsLast()
Performance Tip: Use primitive specializations (comparingInt vs comparing) to avoid boxing. 
// ✅ BEST PRACTICE: Comparator Chaining
Comparator<Employee> comparator = Comparator
    .comparingInt(Employee::getAge)
    .thenComparingDouble(Employee::getSalary)
    .thenComparing(Employee::getName);

// Usage:
List<Employee> emps = getEmployees();
emps.sort(comparator);

// Handling nulls
Comparator<User> c2 = Comparator
    .comparing(User::getLastName, 
        Comparator.nullsLast(
            String.CASE_INSENSITIVE_ORDER));

Stream API - What/Why/When

Slide 19

Declarative Data Processing

📌 What are Streams?

  • NOT a data structure - Just a pipeline descriptor
  • No storage - Conveys elements from source
  • Lazy evaluation - Executes only when terminal op called
  • One-time use - Consumed after terminal operation

💡 Why / ✅ When:

  • Declarative (what, not how)
  • 40% more readable
  • Easy parallelization
  • Processing collections (filter/map)
  • Aggregating data

❌ Don't Use When:

  • Simple loops (overhead)
  • Need to modify source
  • Complex control flow
  • Small collections (< 100)
// ❌ OLD WAY: Imperative (verbose)
List<String> result = new ArrayList<>();
for (String n : names) {
    if (n.length() > 3) {
        result.add(n.toUpperCase());
    }
}
Collections.sort(result);

// ✅ NEW WAY: Declarative (clean)
List<String> result = names.stream()
    .filter(n -> n.length() > 3)
    .map(String::toUpperCase)
    .sorted()
    .collect(Collectors.toList());

Stream Operations - Quick Reference

Slide 20

Building Stream Pipelines

Intermediate (lazy, return Stream)

.filter(n -> n > 10)      // Keep matching
.map(String::toUpperCase) // Transform
.flatMap(List::stream)    // Flatten
.distinct()               // Remove dupes
.sorted()                 // Natural order
.limit(5)                 // First 5 elements
.skip(3)                  // Skip first 3

Terminal (eager, produce result)

.collect(toList())        // Gather to List
.forEach(System::print)   // Side-effect
.reduce(0, Integer::sum)  // Aggregate
.count()                  // Count elements
.anyMatch(n -> n > 5)     // Boolean test
.findFirst()              // First element

Complete Example

// Top 3 expensive "Electronics"
List<Product> top3 = products.stream()
    .filter(p -> "Electronics"
        .equals(p.getCategory()))
    .sorted(Comparator
        .comparing(Product::getPrice)
        .reversed())
    .limit(3)
    .collect(Collectors.toList());

// Count by department
Map<String, Long> countByDept = 
    emps.stream()
    .collect(Collectors.groupingBy(
        Employee::getDepartment,
        Collectors.counting()
    ));

Lazy Evaluation & Short-Circuiting

Slide 21

Performance Optimization

Lazy Evaluation:

  • Intermediate operations not executed until terminal operation
  • Allows optimization (fusion, loop elimination)
  • Only processes elements as needed

Short-Circuiting:

Operations that can complete without processing entire stream

  • Intermediate: limit(n), takeWhile(), dropWhile()
  • Terminal: findFirst(), anyMatch(), allMatch()
// Optimization Example
list.stream()
    .filter(n -> {
        // Will ONLY print until first even 
        // number is found. It aborts early!
        System.out.println("Checking " + n);
        return n % 2 == 0;
    })
    .findFirst(); 

// Stops immediately, doesn't process 
// the entire list. Massive savings on
// large datasets.

Advanced Collectors

Slide 22

Powerful Aggregations

Common Collectors:

  • toList(), toSet(), toMap()
  • joining(delimiter)
  • counting(), summingInt()
  • summarizingInt() (Statistics)

groupingBy & partitioningBy:

  • groupingBy: Like SQL GROUP BY
  • partitioningBy: Binary classification (true/false)
  • Downstream: Passing a secondary collector
// groupingBy (SQL GROUP BY)
Map<String, List<Employee>> byDept =
    employees.stream()
        .collect(Collectors.groupingBy(
            Employee::getDepartment));

// partitioningBy (Binary)
Map<Boolean, List<Integer>> evenOdd =
    nums.stream()
        .collect(Collectors.partitioningBy(
            n -> n % 2 == 0));

// Downstream Collectors
Map<String, Double> avgSalaryByDept =
    emps.stream()
        .collect(Collectors.groupingBy(
            Employee::getDepartment,
            Collectors.averagingDouble(
                Employee::getSalary)
        ));

reduce vs collect

Slide 23

Choosing the Right Aggregation

reduce (Immutable reduction):

  • Creates new value in each step
  • Forms: with/without identity, parallel-friendly combiner
  • When to Use: Simple aggregations (sum, product, min, max, concatenation)
int sum = numbers.stream()
    .reduce(0, Integer::sum);
    
// BAD for building lists!

collect (Mutable reduction):

  • Mutates container (List, Map, etc.)
  • More efficient for mutable accumulation
  • When to Use: Gathering into collections, complex aggregations, grouping
List<String> result = stream
    .collect(Collectors.toList());
    
// FAST for objects!

Parallel Streams - Power & Pitfalls

Slide 24

Multi-Core Processing

✅ When to Use:

  • Large datasets (>10,000 elements)
  • CPU-intensive operations
  • Independent operations
  • Stateless operations

❌ Don't Use When:

  • Small datasets (overhead > benefit)
  • I/O-bound operations (blocks ForkJoinPool)
  • Shared mutable state
  • Ordered operations critical

Performance: 2-8x speedup for suitable workloads, measure first!

// ✅ GOOD: Use reduce for aggregation
int sum = numbers.parallelStream()
    .reduce(0, Integer::sum); // Thread-safe!

// ✅ GOOD: Use collect for gathering
List<Result> res = data.parallelStream()
    .map(this::expensiveOperation)
    .collect(Collectors.toList());

// ❌ WRONG: Shared mutable state
int[] sum = {0};
numbers.parallelStream()
    .forEach(n -> sum[0] += n); // RACE CONDITION!

Parallel Stream Pitfalls & Solutions

Slide 25

Common Mistakes

Pitfall 1: Shared Mutable State

// ❌ WRONG: Race condition
int[] sum = {0};
IntStream.range(0, 1000).parallel()
    .forEach(i -> sum[0] += i); 
// Incorrect result!

// ✅ CORRECT: Thread-safe
int sum = IntStream.range(0, 1000).parallel()
    .reduce(0, Integer::sum);

Pitfall 2: Non-thread-safe Collection

// ❌ WRONG: ArrayList not thread-safe
List<Integer> list = new ArrayList<>();
IntStream.range(0, 1000).parallel()
    .forEach(list::add); // Lost elements!

// ✅ CORRECT: Collector handles thread-safety
List<Integer> list = IntStream.range(0, 1000)
    .parallel()
    .boxed()
    .collect(Collectors.toList());

Key Takeaways & Best Practices

Slide 26

Professional Guidelines

Collections:

  1. Program to interfaces: List<T> not ArrayList<T>
  2. ArrayList is default List, HashSet default Set, HashMap default Map
  3. Specify initial capacity if size known
  4. Override hashCode() when overriding equals()
  5. Use immutable collections (List.of) when possible
  6. Use EnumSet/EnumMap for enums
  7. ConcurrentHashMap over synchronized Map

Streams:

  1. Use for complex data transformations and aggregations
  2. Prefer method references over lambdas
  3. Use primitive streams to avoid boxing
  4. collect() over reduce() for mutable reduction
  5. Don't parallelize prematurely - measure first
  6. Avoid side-effects in stream operations
  7. Use Optional correctly

Performance:

  1. Choose right collection - impacts performance by orders of magnitude
  2. Parallel streams: large datasets + CPU-intensive only
  3. Measure, don't assume - use benchmarks
